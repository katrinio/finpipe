# 📡 Monitoring

Finpipe поддерживает встроенный мониторинг через отдельный Telegram-чат.

Мониторинг позволяет получать системные уведомления и выполнять диагностику без доступа к VPS.

---

## 🎯 Назначение

Monitoring chat используется для:

- системных событий и ошибок
- диагностики состояния приложения
- ежедневной сводки событий за сутки

Пользовательские сценарии и мониторинг полностью разделены.

---

## ⚙️ Как это работает

```
Системное событие
       │
       ▼
  EventLogger ──► app_events (PostgreSQL)
       │
       ▼
  monitoring handlers
       │
       ▼
  Telegram monitoring chat
```

Таблица `app_events` — единый журнал событий системы.

---

## 📨 Куда отправляются уведомления

| Приоритет | Назначение |
|---|---|
| 1 | `MONITORING_CHAT_ID` (если задан) |
| 2 | `BOT_OWNER_TELEGRAM_ID` (fallback) |

---

## 📝 Формат уведомлений

Каждое уведомление содержит:

| Поле | Описание |
|---|---|
| `event_type` | Тип события |
| `severity` | Уровень важности |
| `details` | Дополнительные детали (если есть) |

Пример:

```
⚠️ document_generation_failed
Severity: error
Invoice template not found
```

---

## 🛠️ Мониторинг-команды

Команды работают **только** в monitoring chat. `/help` выводит список прямо в чат.

| Команда | Описание |
|---|---|
| `/health` | Telegram API ✅/❌, БД + кол-во пользователей, время последней активности бота |
| `/events` | Последние 10 событий из `app_events` с временем и severity |
| `/errors` | Последние 10 ошибок с временем, категорией, типом и сообщением |
| `/stats` | Агрегированная статистика по типам событий и документам |
| `/logs [N]` | Последние N строк из Docker-контейнера (по умолчанию 50, макс. 200) |
| `/chatid` | ID текущего чата (для первичной настройки `MONITORING_CHAT_ID`) |
| `/help` | Список доступных команд |

> Неизвестная `/команда` возвращает подсказку со списком доступных. Обычный текст игнорируется.

### `/logs` — требования

Команда использует Docker socket. В `docker-compose.yml` у сервиса `finpipe-bot` должно быть:

```yaml
container_name: finpipe-bot
environment:
  CONTAINER_NAME: finpipe-bot
volumes:
  - /var/run/docker.sock:/var/run/docker.sock:ro
```

---

## 🔒 Изоляция

Monitoring chat не является пользовательским интерфейсом.

| Правило | Описание |
|---|---|
| Входящие из monitoring chat не попадают в user router | Нет конфликтов с пользовательскими командами |
| Пользовательские состояния не обрабатываются | Не портит Telegram workflow |
| Monitoring-команды не работают в пользовательских чатах | Полное разделение потоков |
| Неизвестные `/команды` возвращают `/help` | Нет лишних ошибок, сразу подсказка |
| Обычный текст игнорируется | Нет конфликтов при обсуждении в чате |

## 🏗️ Архитектура

| Компонент | Назначение |
|---|---|
| `EventLogger` | Регистрация событий, запись в `app_events` |
| `app_events` | Таблица-журнал всех событий |
| `register_monitoring_notifications()` | Подписка handlers на события |
| `src/services/monitoring/notifications.py` | Доставка уведомлений в Telegram |
| `src/integrations/telegram/bot.py` | Регистрация мониторинга при старте |

## 📊 Ежедневная сводка

Отдельно от live-уведомлений работает ежедневный отчёт по реальным production-данным.

```
GitHub Actions (cron)
       │  SSH
       ▼
      VPS: docker compose exec finpipe-bot
                  │
                  ▼
       src/workflows/monitoring/daily_report
                  │
                  ▼
         app_events (prod PostgreSQL, последние 24ч)
                  │
                  ▼
         Telegram monitoring chat
```

**Секреты GitHub Actions:**

| Secret | Назначение |
|---|---|
| `VPS_HOST` | Адрес VPS |
| `VPS_USER` | SSH-пользователь |
| `VPS_PORT` | SSH-порт |
| `VPS_SSH_KEY` | Приватный ключ |

**Расписание:** `05:00 UTC` (соответствует 07:00 по Белграду, без учёта DST).

> ⚠️ При смене DST cron-расписание нужно пересматривать вручную.

Почему запускается на VPS, а не в CI: в CI нет доступа к prod PostgreSQL, а отчёт строится по реальным данным за сутки.

---

## 🚧 Текущие ограничения

Monitoring рассчитан на один экземпляр приложения на одном VPS.

Не реализовано:

- внешние системы мониторинга (Grafana, Prometheus)
- централизованный сбор логов (сейчас только через `/logs` из Docker)
- автоматическая агрегация и дедупликация ошибок
